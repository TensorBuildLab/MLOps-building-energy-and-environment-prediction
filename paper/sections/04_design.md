# Study design {#sec:design}

## Datasets

Three public datasets of measured data were chosen to cover many prediction targets, three climates, different levels of data quality, and a portfolio of buildings (@tbl:datasets). All three can be downloaded by a script without an account, and the script verifies their checksums, so every result can be reproduced from the repository; the raw data are not redistributed. The three-year record of LBNL Building 59 [@luo2022] was considered but not used, because its repository does not allow scripted download.

## Roles of the agent and the authors

An LLM agent (Claude Opus 5.5, Anthropic, operated in Claude Code) followed the Agent Skill in the repository to load the data, decode the point names, write the declarations and make the judgment calls. These decisions are frozen in the case-study scripts as declarations and written notes, and are copied into every run record. Examples include reading the undocumented units of the Aalborg data from the magnitudes of the values (power in W, airflow in m^3^ h^−1^), converting timestamps with a UTC offset to local time while keeping the time zone so that daylight-saving hours are handled exactly, excluding the presence flag of ROBOD from the inputs of the people-count virtual sensor because it derives from the same camera ground truth, and accepting missing camera counts in the Aalborg data as documented gaps. The agent's conversation transcripts are not archived, so the record shows its decisions but not its reasoning. The authors set the research questions and the datasets, and reviewed the code, results and text.

The same agent also wrote the package, so the case studies show the framework operated by an agent rather than an independent test of agents; @sec:validity discusses this threat to validity. Several detectors were revised on ROBOD and Aalborg data (Supplementary Material, Table S1), so on those two datasets the data checks are partly in-sample. BDG2 prompted none of those revisions. Its declarations and notes were set before its first run and not changed afterwards; between runs, the building sample was changed to 20 buildings drawn round-robin across sites to save time, and the candidate list gained the change-based gradient-boosting model that had been added to the package for the pilot. BDG2 is therefore closer to held-out data than the other two datasets, but not strictly held out.

The chilled-water meters of ROBOD read exactly zero for whole days while the air-handling unit (AHU) was running with its cooling-coil valve open: 9 days in Room 3, 1 in Room 4 and 10 in Room 5. A day was counted as an outage when the AHU fan ran above 5 Hz with the valve more than 15% open for at least 1 h and no chilled-water energy was recorded during those hours, which is physically implausible. No single-column check can flag such a fault, because zero is a normal reading for an idle meter. The case-study agent missed it, whereas all four independent pilot agents that worked on Room 5 found it (@sec:res-pilot). The case-study loader now sets those days to missing, the three affected tasks were re-run, and the earlier results are kept in the repository for comparison.

## Prediction tasks

ROBOD contributed nine tasks per room for five rooms (45 tasks): forecasts 30 min ahead of CO~2~, temperature, humidity, PM2.5, people count and presence (binary); a virtual people counter that estimates the current count from Wi-Fi connections, CO~2~, sound, light and plug loads; and forecasts 1 h ahead of chilled-water and plug-load energy. The Aalborg data contributed 27 tasks: forecasts 1 h ahead of CO~2~, temperature, people count and room use (motion sensor, binary) for each of six rooms, and three building-level tasks, namely ventilation electric power 1 h ahead and district-heating power 1 h and 24 h ahead. BDG2 contributed one task per building: hourly electricity 24 h ahead, with one configuration decided by the agent for the whole dataset and applied unchanged to every building. Because the dataset contains no weather forecasts, weather enters only up to the forecast time.

All tasks used 15-min resolution (hourly for BDG2), the default 70/15/15% time-ordered split and the default candidates, with small hyperparameter searches of three to six settings per model; BDG2 used ridge regression and the two gradient-boosting models, and the Aalborg tasks omitted the random forest, both to save time. With small searches and no weather forecasts the models are deliberately ordinary, so a strong baseline has a real chance to win. The results therefore show how often a typical, untuned model is worth deploying, not how good the best possible model is.

## Experiments {#sec:experiments}

Each experiment answers one research question.

E1 (RQ1, many targets and buildings). Every task was run through the full workflow. The results reported are skill against the strongest baseline, a Diebold–Mariano test of the model against that baseline on the test set [@diebold1995], errors in physical units, the rolling-origin backtest, the coverage of the 90% interval, the Guideline 14 results for energy and the gate decisions.

E2 (RQ2, evaluation protocol). The same random forest, with the same inputs and on the same rows, was evaluated in three ways: five-fold cross-validation with shuffled rows, equivalent to the random split of the preliminary study; the same with features first selected on all rows, the full recipe of that study; and five-fold blocked cross-validation, which removes from training a buffer around each test block equal to the longest input look-back plus the horizon. E2 used the regression tasks of ROBOD Rooms 4 and 5, which have the most data, and those of Aalborg Room A and its building systems. Because all three protocols score the same rows, differences arise from the protocol alone.

E3 (RQ3, planted faults). Eight known faults were planted at random positions in the Aalborg Room A data of February to June 2023, with ten random seeds: a change from °C to °F in the last 40% of the zone temperature, a three-day stuck sensor, ten spikes, twenty −999 placeholder values in the target, twenty "OFFLINE" text entries, a 12-h outage, a day of duplicated rows and thirty rows out of order. A fault counts as detected when the data check on the faulty data reports an issue of that type on that column which it did not report on the clean data; detection is therefore per column and type, not per located sample. To measure the cost of the faults, the same random forest with the same leakage-safe inputs, forecasting CO~2~ 1 h ahead, was trained in four ways: on clean data; on faulty data prepared by a quick script that coerces text, sorts, averages duplicates, resamples and fills forward; by the same script after a unit fix; and by the framework after the same unit fix resolves its one blocking error. The unit fix stands in for the agent's decision on the blocking error and was coded by the authors (readings above 50 converted from °F to °C). All four arms were scored against the clean target over the same test period, and the clean-data model was refitted with each of the ten seeds to show how much the random seed alone moves the result.

E4 (RQ4, lifecycle). Two Aalborg series, district-heating power and Room A CO~2~, were forecast 1 h ahead. A model trained on late February to April 2023 was promoted to production. Each month from May to December, the production model was scored on that month and the drift check of @sec:gates was run; when it recommended retraining, a challenger was trained on all data to date and promoted only if it passed the gates and beat the champion. Four other arms were scored on the same months: a static model that was never retrained, a model retrained every month on all earlier data without gates, persistence, and a counterfactual fallback rule that serves persistence in month $m$ if the production model was worse than persistence in month $m-1$. The fallback rule uses only past months and could therefore have run in operation.

E5 (RQ5, formative pilot with independent agents). To separate the framework from the agent that built it, fresh agent instances were each given a folder that contained only a raw export with planted faults and a task description. Each agent had to deliver a *predict* function and a report stating the RMSE it expected on future data. Task T1 was CO~2~ in Aalborg Room B 1 h ahead, with training data up to May 2023 and June hidden; task T2 was chilled-water energy in ROBOD Room 5 1 h ahead, with the last fifth of the days hidden. In the agent-alone arm the agent had pandas and scikit-learn only, and bemlops was forbidden; in the framework arm the agent was told to follow the Agent Skill. Each arm ran with Claude Opus 5.5 and Claude Sonnet 5.5, giving eight runs. The agents could not see the hidden data or the evaluation code, and their launch prompts are published with the code. Each deliverable was scored on whether it ran; its RMSE on the hidden period against the clean target, as skill against persistence and against the time-of-day profile computed without the dead-meter days; an automatic leakage test that perturbs every value at or after $T$ − 45 min for 15 random hidden-period times $T$ and checks that the forecast for $T$ is unchanged; and the ratio of the achieved to the self-reported RMSE. The code and reports were also audited by hand, and the tokens, tool calls and wall-clock time of each run were recorded. With one run per cell, E5 is a formative usability study, not a benchmark: it asks whether the effects the framework is designed for appear at all with agents that did not write it.

## Statistical analysis

The Diebold–Mariano test [@diebold1995] compares the losses of the model and of the reference baseline on the test set through the loss differential $d_t = e_{t,\mathrm{model}}^2 - e_{t,\mathrm{ref}}^2$ (Brier losses for binary targets),

$$ \mathrm{DM} = \frac{\bar{d}}{\sqrt{\hat{\sigma}^2_{\mathrm{HAC}}/n}} $$ {#eq:dm}

where $\hat{\sigma}^2_{\mathrm{HAC}}$ is a heteroskedasticity- and autocorrelation-consistent variance with a Bartlett kernel and a lag equal to the larger of the horizon and the Newey–West rule-of-thumb bandwidth $\lfloor 4(n/100)^{2/9} \rfloor$. Proportions are reported with 95% Wilson intervals [@wilson1927]. In E3, arms that share a seed, and therefore the same planted faults, are compared with paired Wilcoxon signed-rank tests. In E5, the root-mean-square-error difference between arms for the same task and model is given a 95% interval by a paired day-block bootstrap with 2,000 resamples of whole days.
